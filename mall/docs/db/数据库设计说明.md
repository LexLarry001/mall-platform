# 数据库设计说明

多商家 B2B2C 家具商城的数据存储方案：**MySQL 承载强关系与事务数据，MongoDB 承载文档型数据，Redis 承载缓存、登录态与并发控制**。

- MySQL：22 张表（账号与 RBAC、商品、交易、支付、物流、售后、评价、向量）
- MongoDB：3 个集合（商品富文本详情、物流轨迹、审核留痕）
- Redis：19 类 Key（登录态、购物车、热点缓存、订单锁、AI 缓存与限流）
- 设计脚本：`mall/docs/db/m*.sql` 与 `mall/docker/mysql/init/01~11-*.sql`，两者内容保持一致

---

## 一、总体设计原则

| 原则 | 落地方式 |
|---|---|
| 关系型数据进 MySQL | 账号、商品、订单、支付、退款、评价等有强一致与事务要求的数据 |
| 文档型数据进 MongoDB | 富文本详情、物流轨迹、审核留痕：结构不固定、整篇替换、追加写多 |
| 热数据进 Redis | 登录态、购物车、商品详情缓存、热搜榜、分布式锁、AI 结果缓存 |
| 主键统一 | 业务主键 `BIGINT` 雪花 ID（MyBatis-Plus `ASSIGN_ID`），不使用自增 |
| 金额统一 | `DECIMAL(10,2)`，禁止浮点 |
| 状态统一 | `TINYINT` 状态码 + 应用层状态机，不使用数据库枚举 |
| 逻辑删除 | 主数据表带 `deleted`；订单、支付、退款、物流、评价等事实表不删除 |
| 不建物理外键 | 由应用层与事务保证引用完整性，避免分库与批量写入受限 |
| 快照优先 | 订单项、收货地址、店铺名、商品名等在下单时固化，避免上游改价改名影响历史数据 |

字段命名：数据库使用 `snake_case`，Java 实体使用 `camelCase`，由 MyBatis-Plus 自动映射；表 `order` 为 MySQL 保留字，DDL 与查询均使用反引号。

## 二、MySQL 设计

### 2.1 表清单（22 张）

| 域 | 表 | 说明 |
|---|---|---|
| 账号 | `user` | 买家账号，`username` 唯一 |
| 账号 | `merchant` | 入驻商家账号，含入驻审核状态与申请草稿字段 |
| 账号 | `sys_user` | 平台管理员账号，不开放自助注册 |
| 权限 | `sys_role` | 平台角色，`code` 唯一（如 `ROLE_SUPER`） |
| 权限 | `sys_permission` | 权限与菜单共用一表，`type = MENU / BUTTON` |
| 权限 | `sys_user_role` | 管理员与角色多对多 |
| 权限 | `sys_role_permission` | 角色与权限多对多 |
| 商家 | `shop` | 店铺，仅审核通过后生成，`merchant_id` 唯一 |
| 商品 | `category` | 平台类目，`parent_id` 自关联树 |
| 商品 | `product` | 商品 SPU，含审核状态、评分与评价数冗余 |
| 商品 | `product_sku` | 商品 SKU，含规格 JSON、价格、库存 |
| 商品 | `product_spec` | SPU 规格定义（规格名 + 可选值 JSON 数组） |
| 商品 | `file_record` | 上传文件记录，文件本体在本地 `uploads/` |
| 交易 | `user_address` | 买家收货地址，默认地址由应用事务保证唯一 |
| 交易 | `order` | 主订单，一次结算一条，含跨店汇总金额 |
| 交易 | `sub_order` | 子订单，按店铺拆单，一店一单 |
| 交易 | `order_item` | 订单项，保存商品名称、主图、规格、单价快照 |
| 支付 | `payment_record` | 支付流水，与主订单 1:1，`order_no` 唯一 |
| 物流 | `shipment` | 发货单，与子订单 1:1，`sub_order_id` 唯一 |
| 售后 | `refund_order` | 退款单，订单项粒度，`refund_no` 唯一幂等 |
| 评价 | `product_review` | 商品评价，`order_item_id` 唯一防重复评价 |
| 向量 | `product_embedding` | 商品语义向量，JSON 数组存 `LONGTEXT`，应用启动加载进内存 |

### 2.2 核心表结构

#### 账号与权限

```sql
user(id, username, password, status, create_time, update_time, deleted)
merchant(id, username, password, contact_phone, audit_status, status,
         subject_name, license_no, license_img, shop_name, shop_logo, shop_intro,
         audit_remark, create_time, update_time, deleted)
sys_user(id, username, password, status, create_time, update_time, deleted)

sys_role(id, name, code, status, create_time, update_time, deleted)
sys_permission(id, parent_id, name, code, type, path, sort, status,
               create_time, update_time, deleted)
sys_user_role(user_id, role_id, create_time)                 -- 主键 (user_id, role_id)
sys_role_permission(role_id, permission_id, create_time)     -- 主键 (role_id, permission_id)
```

- 三端账号分表存储（买家 / 商家 / 管理员），互不越权。
- 密码统一 BCrypt（`VARCHAR(64)`），不存明文。
- `sys_permission` 的 `type=MENU` 节点同时作为菜单与权限码；`type=BUTTON` 只做细粒度授权，不出现在侧边栏。
- 权限变更后删除 `mall:perms:{adminId}` 缓存，使授权实时生效。

#### 商品

```sql
product(
  id BIGINT PK, shop_id BIGINT, category_id BIGINT,
  name VARCHAR(64), sub_title VARCHAR(128), main_img VARCHAR(255), img_list VARCHAR(1000),
  price DECIMAL(10,2),              -- SKU 最低价冗余，列表页免聚合
  sales INT, avg_rating DECIMAL(2,1), comment_count INT,
  status TINYINT,                   -- 0 草稿/1 待审核/2 已上架/3 审核驳回/4 商家下架/5 平台违规下架
  audit_remark VARCHAR(255),
  review_version INT,               -- 评价版本号，新增/隐藏评价时 +1
  create_time, update_time, deleted
)

product_sku(
  id BIGINT PK, spu_id BIGINT, spec_json VARCHAR(500),
  price DECIMAL(10,2), stock INT, sku_img VARCHAR(255),
  create_time, update_time, deleted
)

product_spec(
  id BIGINT PK, spu_id BIGINT, spec_name VARCHAR(32), spec_values VARCHAR(500),
  create_time, update_time, deleted
)
```

- SPU 与 SKU 一对多；`spec_json` 保存规格值组合，如 `{"材质":"实木","尺寸":"1.8m"}`。
- `sales / avg_rating / comment_count / review_version` 为读性能冗余字段，由订单与评价域维护。
- 商品状态只允许通过审核与上下架接口推进，买家查询强制 `status = 2`。

#### 交易

```sql
user_address(id, user_id, receiver, phone, province, city, district, detail,
             is_default, create_time, update_time)

`order`(
  id, order_no UNIQUE, user_id, total_amount, pay_amount, status,
  receiver, phone, full_address,   -- 下单时地址快照
  expire_time,                     -- 创建时间 + 30 分钟，超时关单依据
  create_time, update_time
)

sub_order(
  id, sub_order_no UNIQUE, order_id, shop_id, shop_name, amount, status,
  create_time, update_time
)

order_item(
  id, sub_order_id, spu_id, sku_id,
  product_name, main_img, spec_json, price, quantity,   -- 商品快照
  create_time
)
```

- 主订单与子订单是 1:N；结算时按 `shop_id` 拆单。
- 地址、商品信息采用快照，删除地址或商家改价不影响历史订单。
- 订单表不做逻辑删除，保留完整交易事实。

#### 支付、物流、售后

```sql
payment_record(
  id, order_no UNIQUE, trade_no, amount, status,   -- 0 待支付 / 1 支付成功
  notify_raw TEXT, pay_time, create_time, update_time
)

shipment(
  id, shipment_no UNIQUE, sub_order_id UNIQUE, sub_order_no,
  provider,                 -- manual / amap
  carrier_code, carrier_name, tracking_no,
  from_address, to_address, from_lng, from_lat, to_lng, to_lat,
  current_status,           -- SHIPPED/IN_TRANSIT/OUT_FOR_DELIVERY/DELIVERED/EXCEPTION
  trace_count, create_time, update_time
)

refund_order(
  id, refund_no UNIQUE, order_id, order_no, sub_order_id, sub_order_no,
  order_item_id, spu_id, sku_id, product_name, shop_id, user_id,
  quantity, refund_amount, reason, evidence_images TEXT,
  status,                   -- 0 待审核 / 2 已退款 / 3 已驳回 / 4 退款失败
  sub_status_before, audit_remark, audit_time,
  alipay_trade_no, refund_time, fail_code, fail_msg,
  create_time, update_time
)
```

- `refund_no` 同时作为支付宝 `out_request_no`，保证重复退款请求幂等。
- `shipment.trace_count` 为轨迹节点数缓存，真实轨迹节点存 MongoDB。

#### 评价

```sql
product_review(
  id, user_id, user_name, order_id, sub_order_id, order_item_id UNIQUE,
  spu_id, sku_id, shop_id, shop_name, product_name, main_img,
  rating TINYINT, content VARCHAR(1000), images VARCHAR(1000),
  anonymous TINYINT, tags VARCHAR(500), sentiment TINYINT,
  status TINYINT,          -- 1 展示 / 2 平台隐藏
  hide_reason, merchant_reply, reply_time,
  create_time, update_time
)
```

- `order_item_id` 唯一键从数据库层杜绝同一订单项重复评价。
- `tags / sentiment` 由 AI 写入；AI 不可用时留空，不影响评价提交。
- 评价新增、隐藏、恢复后递增 `product.review_version` 并重算评分，摘要缓存随版本号自然失效。

#### 商品向量

```sql
product_embedding(
  spu_id BIGINT PK, model VARCHAR(64), dim INT,
  vector LONGTEXT,          -- JSON 数组，如 [0.12,-0.03,...]
  text_hash CHAR(64),       -- 向量化文本 SHA-256，用于判断是否需要重建
  status TINYINT,           -- 0 待生成 / 1 成功 / 2 失败
  retry_count INT, error_msg VARCHAR(255),
  create_time, update_time
)
```

- 向量落 MySQL，应用启动时加载到内存 `VectorStore`，检索使用内存余弦相似度。
- 事务提交后异步生成向量，失败由补偿任务重试（最多 3 次）。
- `VectorStore` 为接口，后续可替换为 Milvus / pgvector，不改业务代码。

### 2.3 关系模型

```
user 1 ─── N user_address
user 1 ─── N `order` 1 ─── N sub_order 1 ─── N order_item
                  │              │                │
                  │              │                └── 1:0..1 product_review
                  │              ├── 1:1 shipment ── 1:N logistics_trace(Mongo)
                  │              └── 1:N refund_order
                  └── 1:1 payment_record

merchant 1 ─── 1 shop 1 ─── N product 1 ─── N product_sku
                              │        └── N product_spec
                              ├── N product_embedding
                              └── N:1 category（parent_id 自关联树）

sys_user N ─── N sys_role N ─── N sys_permission
```

### 2.4 索引设计

| 表 | 索引 | 目的 |
|---|---|---|
| `user` / `merchant` / `sys_user` | `uk_*_username` | 登录唯一性 |
| `sys_permission` | `uk_code`、`idx_parent` | 权限码唯一、菜单树查询 |
| `shop` | `uk_merchant` | 一个商家一家店 |
| `category` | `idx_parent` | 按父节点取子类目 |
| `product` | `idx_product_category_status`、`idx_product_shop_status` | 买家分类列表、商家商品列表 |
| `product_sku` / `product_spec` | `idx_*_spu` | 按 SPU 取规格与 SKU |
| `file_record` | `idx_uploader` | 按上传者查文件 |
| `user_address` | `idx_address_user` | 收货地址列表 |
| `order` | `uk_order_no`、`idx_order_user_status` | 单号唯一、买家订单分状态查询 |
| `sub_order` | `uk_sub_order_no`、`idx_sub_order_order`、`idx_sub_order_shop_status` | 拆单查询、商家待办 |
| `order_item` | `idx_order_item_sub` | 子订单明细 |
| `payment_record` | `uk_payment_order_no` | 一单一支付、回调幂等 |
| `shipment` | `uk_shipment_no`、`uk_sub_order`、`idx_sub_order_no` | 一子单一次发货 |
| `refund_order` | `uk_refund_no`、`idx_refund_item`、`idx_refund_sub`、`idx_refund_shop_status`、`idx_refund_user` | 退款幂等与三端查询 |
| `product_review` | `uk_review_item`、`idx_review_spu_status_time`、`idx_review_user_time`、`idx_review_shop_status_time` | 防重复评价、商品评价分页、买家/商家列表 |
| `product_embedding` | `idx_status` | 补偿任务扫描失败向量 |

组合索引均按「过滤字段在前、排序字段在后」设计，覆盖 `WHERE ... ORDER BY create_time DESC` 的常用查询。

### 2.5 状态机

**主订单 `order.status`**

```
0 待支付 ──支付成功──> 1 已支付 ──全部子订单完成──> 2 已完成
   │                      │
   ├──超时/取消──> 3 已取消  └──全部子订单退款──> 4 已退款
```

**子订单 `sub_order.status`**

```
0 待支付 ──支付成功──> 1 待发货 ──商家发货──> 2 待收货 ──确认收货──> 3 已完成
   │                      │                     │
   ├──超时/取消──> 4 已取消  ├──退款申请──> 5 退款中
   │                      ├──全部退款──> 6 已退款（终态）
   │                      └──部分退款──> 7 部分退款（剩余商品仍可履约）
```

**退款 `refund_order.status`**

```
0 待审核 ──商家同意 + 支付宝退款成功──> 2 已退款
   ├──商家驳回──> 3 已驳回
   └──支付宝退款失败──> 4 退款失败
```

**物流 `shipment.current_status`**

```
SHIPPED ──> IN_TRANSIT ──> OUT_FOR_DELIVERY ──> DELIVERED（终态）
                       └──> EXCEPTION
```

**商品 `product.status`**

```
0 草稿 ──提交审核──> 1 待审核 ──通过──> 2 已上架
                        └──驳回──> 3 审核驳回
2 已上架 ──商家下架──> 4 商家下架
        └──平台违规──> 5 平台违规下架
```

所有状态推进使用条件更新（如 `WHERE id = ? AND status = 0`），保证并发与重复请求下只成功一次。

### 2.6 一致性与并发控制

| 场景 | 方案 |
|---|---|
| 库存防超卖 | `UPDATE product_sku SET stock = stock - ? WHERE id = ? AND stock >= ?`，影响行数为 0 即失败 |
| 重复提交订单 | Redis `SET NX EX 5s`（`mall:order:submit:{userId}`），未抢到直接拒绝 |
| 支付回调重复 | `payment_record.order_no` 唯一 + 条件更新，仅 `0 → 1` 生效，迟到回调只记日志 |
| 退款重复请求 | `refund_no` 作为 `out_request_no`，支付宝侧幂等；本地唯一键兜底 |
| 重复评价 | `product_review.order_item_id` 唯一键 |
| 超时关单 | 订单创建时写入 Redis ZSet，定时任务每 60 秒扫描到期订单，条件更新 `0 → 3` 后移除 |
| 远程退款与本地事务 | 退款单落库与支付宝调用用 `TransactionTemplate` 分段，远程失败可重试，不产生长事务 |
| 评分聚合 | 评价变更后重算 `avg_rating / comment_count`，并递增 `review_version` |

## 三、MongoDB 设计

### 3.1 选型理由

以下数据不适合放 MySQL：结构随业务变化、整体读写、追加写多、无需跨文档事务。统一使用 `mongodb://localhost:27017/mall`，开启 `auto-index-creation`，由 `@Document` / `@Indexed` 自动建索引。

### 3.2 集合结构

#### product_detail（商品富文本详情）

```json
{
  "_id": ObjectId,
  "spuId": 1958...,          // 对应 MySQL product.id
  "html": "<p>...</p>",      // wangEditor 富文本
  "gallery": ["/static/..."],// 详情图集
  "updateTime": ISODate
}
```

- 索引：`{ spuId: 1 }`，唯一。
- 与 `product` 一一对应；商品删除或下架时详情不参与查询。
- 整篇覆盖写，不做字段级更新。

#### logistics_trace（物流轨迹）

```json
{
  "_id": ObjectId,
  "shipmentNo": "SH1958...",   // 对应 shipment.shipment_no
  "nodeType": "STATUS",        // STATUS / ROUTE / POSITION
  "status": "IN_TRANSIT",      // 物流状态
  "desc": "包裹已到达杭州转运中心",
  "address": "杭州转运中心",
  "lng": 120.15, "lat": 30.28,
  "polyline": [[120.1,30.2], ...],  // ROUTE 节点：高德规划折线
  "ts": ISODate
}
```

- 索引：`{ shipmentNo: 1 }`、`{ ts: 1 }`；按发货单查询后按时间倒序返回。
- 写入策略：发货追加 `STATUS:SHIPPED`，状态推进追加对应节点；高德模式发货时额外写入一条 `ROUTE` 节点保存折线。
- 轨迹只追加不修改，天然保留完整履约过程。

#### merchant_audit_log（审核留痕）

```json
{
  "_id": ObjectId,
  "targetType": "PRODUCT",     // MERCHANT_APPLY / PRODUCT
  "targetId": 1958...,
  "action": "REJECT",          // SUBMIT / PASS / REJECT / VIOLATION_OFF
  "operator": "ADMIN:1",
  "remark": "主图不清晰",
  "createTime": ISODate
}
```

- 索引：`{ targetId: 1 }`。
- 入驻审核与商品审核共用，按对象回溯全部审核动作。

### 3.3 与 MySQL 的边界

- MongoDB 不存金额、库存、状态机等需要事务的数据。
- MySQL 保存业务主键与状态，MongoDB 通过 `spuId`、`shipmentNo`、`targetId` 关联。
- 写入顺序：先完成 MySQL 状态变更，再写 Mongo 文档；Mongo 写入失败只记日志，不回滚主流程。

## 四、Redis 设计

### 4.1 Key 规范

`mall:{业务域}:{标识}`，业务域之间用冒号分隔；带账号维度的 Key 使用 `{accountType}:{accountId}`；带时间的 Key 使用 `yyyyMMdd` 或分钟戳。

### 4.2 Key 清单（19 类）

| Key | 类型 | TTL | 用途 |
|---|---|---|---|
| `mall:login:{token}` | String(JSON) | 12h | token → 登录态，鉴权时反查 |
| `mall:token:{TYPE}:{accountId}` | String | 12h | 账号当前有效 token，用于单点登录与强制下线 |
| `mall:refresh:{TYPE}:{accountId}` | String | 7d | 账号当前刷新令牌，二次登录覆盖旧值 |
| `mall:captcha:{key}` | String | 5min | 图形验证码答案，校验后立即删除 |
| `mall:cart:{userId}` | Hash | 无 | 购物车，field=skuId，value=`{"quantity":2,"checked":true}` |
| `mall:category:tree` | String(JSON) | 无 | 类目树缓存，类目变更后删键重建 |
| `mall:product:{spuId}` | String(JSON) | 30min | 商品详情聚合缓存，商品变更后删键 |
| `mall:hot:search` | ZSet | 无 | 热搜词榜，`ZINCRBY +1`，取 Top10 |
| `mall:order:submit:{userId}` | String | 5s | 下单防重锁，`SET NX` |
| `mall:order:timeout` | ZSet | 无 | 超时关单锚点，member=订单号，score=截止时间戳 |
| `mall:perms:{adminId}` | Set | 30min | 管理员权限码集合，角色/权限变更后删除 |
| `mall:ai:embed:{model}:{sha256}` | String | 24h | 文本向量缓存 |
| `mall:ai:chat:{sha256}` | String | 1h | 大模型对话结果缓存（含提示词与温度哈希） |
| `mall:ai:rate:{provider}:{minute}` | String | 60s | 单 provider 每分钟限流，默认 60 次/分钟 |
| `mall:ai:circuit:fail:{provider}` | String | 300s | 连续失败计数，达到 5 次触发熔断 30 秒 |
| `mall:review:summary:{spuId}:v{version}` | String(JSON) | 10080min | AI 评价摘要，按评价版本隔离 |
| `mall:review:recommend:{md5}` | String(JSON) | 30min | AI 导购结果，键含 query/预算/类目/条数 |
| `mall:review:ai:daily:{yyyyMMdd}` | String | 24h | AI 全局日配额，默认 500 次 |
| `mall:review:ai:user:{userId}:{yyyyMMdd}` | String | 24h | 单用户日配额，默认 50 次 |

### 4.3 关键用法

**登录与顶号**

登录时写 `mall:login:{token}` 与 `mall:token:{TYPE}:{accountId}`。鉴权时除校验 token 本身，还比较账号指针是否仍等于该 token，实现「后登录顶掉先登录」。退出或强制下线时同时清除登录态、token 指针与刷新令牌。

**购物车**

购物车不落 MySQL，Redis Hash 即唯一存储。field 为 skuId，加购同款合并数量；列表读取时联查 SKU/SPU，标记下架、删除、库存不足为不可结算；下单成功后按已勾选 field 执行 `HDEL`。

**缓存一致性**

统一 Cache-Aside：读缓存未命中回源并回填；写操作（商品编辑、审核、上下架、类目变更、权限变更）成功后直接删除对应 Key。缓存 JSON 解析失败按未命中处理并重建，错误结果（如商品已下架）不缓存。

**AI 与评价缓存**

- 向量与对话结果以「模型 + 内容哈希」为键，避免重复调用第三方。
- 评价摘要 Key 带 `review_version`：新增或隐藏评价时版本号 +1，旧键自然失效，无需精确删除。
- 导购结果按「query + 预算 + 类目 + 条数」哈希缓存 30 分钟。
- 调用前做每分钟限流与连续失败熔断；超限或熔断时直接走规则降级，不阻塞主流程。

**故障降级**

| 故障 | 行为 |
|---|---|
| Redis 不可用 | 商品/类目缓存回源 MySQL；AI 缓存与限流失效则跳过缓存直接调用或降级 |
| Redis 中购物车丢失 | 购物车为空，不影响订单与商品数据（购物车本就不落库） |
| 缓存内容损坏 | 按未命中处理，重新构建 |
| AI 第三方超时/失败 | 评价摘要回落统计摘要，导购回落规则排序，商品文案回落模板 |

## 五、数据安全

- 密码仅存 BCrypt 哈希，不存明文，不可逆。
- 第三方密钥（支付宝、高德、DeepSeek、百炼）全部通过环境变量注入，数据库与仓库均不保存密钥。
- 订单、退款、评价中的手机号与地址属于业务快照，仅在对应权限接口返回；公开仓库中的演示数据均为虚构数据。
- 权限校验在应用层按账号类型、店铺归属、订单归属逐层校验，数据库不依赖外键做访问控制。
- 敏感操作（审核、退款、强制下线）均记录操作者与时间，审核动作另存 MongoDB 留痕。
